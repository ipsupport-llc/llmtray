# 0026 — Mail: the chat reads, sorts and drafts replies in Apple Mail

**Status: proposed** (2026-10-15). The user's idea and shape: "fat tools",
like the documents and folder tools. Waiting for the spike below and the
user's review.

## Decision

The chat model gets Apple Mail as a tool group: "what came in today that
needs an answer", "find the invoice from Hetzner", "move the newsletters
to Later and mark them read", "draft a reply to Anna saying Thursday
works". It talks to Mail.app through its scripting dictionary, so every
account the user already has in Mail works (iCloud, Gmail, Exchange,
IMAP), with no passwords, no OAuth and no server of ours.

- **Opt-in**, like every feature that can do damage
  ([feature rule](0014-folder-tools.md)): off until turned on in
  Settings › Tools › Mail. Without it no mail tool is declared and Mail is
  never sent an Apple event.
- **A tool group, loaded when needed** ([0020](0020-documents.md),
  "Tools loaded when needed"): group `mail`, phrase "Apple Mail: read,
  search, sort, draft replies". On demand by default (`load_tools` or the
  + menu's **Use Mail…**); a profile can set it to Always.
- **Two tools, the folder tools' split** ([0014](0014-folder-tools.md),
  "Tools"): one to look, one to change. Fewer tools are understood better
  by small models and cost less context.
- **Nothing is ever sent.** Replies and new messages are saved as drafts
  in Mail; the user sends them from Mail. There is no send mode, by any
  path.
- **Every change is a plan the user approves**: the folder tools' plan
  card, with the same rules (whole, in part, or not at all; nothing
  happens before).
- **Mail is untrusted text**: subjects, senders and bodies are data,
  never instructions -- the trust barrier of 0012/0014 (see "Trust").
- **Developer ID build only.** The App Store flavor's sandbox can't send
  Apple events to Mail without a temporary-exception entitlement that
  review won't pass; there the feature isn't shown.

## Tools

```
mail(
  mode: accounts | list | search | read,
  mailbox?,          // "Inbox" (default), "Later", "Archive", account/mailbox
  account?,          // when two accounts have the same mailbox name
  query?,            // search: words in subject or sender (body: see spike)
  from?, since?,     // search filters; since = "2026-10-01" or "7d"
  unread_only?, flagged_only?,
  id?,               // read: one message
  cursor?            // paging
)
```

- `accounts` -- accounts and their mailboxes with unread counts, one
  line each, paged.
- `list` -- a mailbox, newest first: one line per message with a short
  id (`m12`), date, sender (name and address), subject, read and flag
  marks, attachments count. No bodies. 25 per page.
- `search` -- the same lines for matches across the mailboxes asked (all
  of the allowed accounts' inboxes by default), within a time cap
  (partial result with a note when hit).
- `read` -- one message: headers (from, to, cc, date, subject), the body
  as plain text, quoted history and signatures cut, at most 6,000
  characters (with how much was cut), attachments by name and size only.
  Never attachment contents, never HTML, never remote content (nothing is
  fetched for a message, no tracking pixel fires).

```
change_mail(ops: [
  { op: move,        ids: [..], to: mailbox },
  { op: mark,        ids: [..], read?: bool, flagged?: bool },
  { op: trash,       ids: [..] },
  { op: reply_draft, id, body, reply_all? },
  { op: new_draft,   to: [..], cc?: [..], subject, body }
])
```

The list is the plan. The card shows each op in words ("move 14 messages
to Later", the messages expandable; a draft shown in full, recipients
first). Approve whole, in part, or none. After approval: done in Mail,
journaled, and **Undo** for the last plan (moves and trash moved back,
marks restored, drafts deleted while still drafts). Trash is Mail's own
Deleted Messages, never a permanent delete.

Ids are the chat's, not Mail's: `m12` maps to (account, mailbox, Mail's
message `id`, the `Message-ID` header) recorded when listed. At execution
the message is found again by both and must still match, or the op fails
closed ("message changed or moved") -- the folder tools' identity rule
(0014, Hardening 1) in Mail's terms.

## Trust

Mail is the most attacked text a user has: anyone can put words in front
of the model. The 0014 barrier, applied as is:

1. Once a `mail` call returned anything in a turn, network tools and
   generators are refused for that turn (a mail saying "search the web
   for <the user's other mail>" leaks nothing), and so is `change_mail`
   (a mail saying "move everything to Trash" moves nothing). Declared and
   refused in code, as `change_files` is ([0007](0007-chat-tools.md),
   "One list per turn").
2. So a change comes from the user's next message: the model reads,
   says what it would do ("14 newsletters, move them to Later?"), the
   user says yes, the model proposes, the user approves the card. Two
   human steps, the second showing exactly what will happen.
3. A draft's text is the model's, written after reading mail: the card
   shows it in full, and it is only a draft.
4. Mail text never reaches memory: memory reads only the user's own
   messages ([0024](0024-memory.md)).
5. Temporary chats: `mail` only, no `change_mail` (0014, Hardening 8).

## How it talks to Mail

- **Fixed scripts in the app, data as arguments.** Each mode is one
  JavaScript for Automation script shipped in the app, run by `osascript
  -l JavaScript <script> <args…>`; the model's strings arrive as `argv`
  and are never put into script text, so a subject with quotes can't
  become code. The script prints JSON; the app parses it with limits.
- **A child process, supervised** like document rendering (0020): its
  own process group, killed at the time cap (10 s for a list, 30 s for a
  search), 2 MB of stdout. Mail hangs on a stuck account; the chat must
  not.
- **Permission.** The first call triggers macOS's "LLMTray wants to
  control Mail" prompt (Automation). The app gets the
  `com.apple.security.automation.apple-events` entitlement and an
  `NSAppleEventsUsageDescription`. A denial is answered to the model
  ("the user hasn't allowed Mail access; they can in System Settings ›
  Privacy › Automation") and shown in Settings with a button there.
- **Mail not running**: an Apple event launches it. The tool says so
  the first time ("opened Mail"), and Settings has "Only when Mail is
  open" (default off).
- **Accounts the user allows**: Settings lists Mail's accounts with a
  checkbox each (all on by default when the feature is turned on); an
  account left out is invisible to both tools.

## Spike (before the code)

On the user's Mac, with their permission, read-only:

1. Speed of `list` (25 newest of an Inbox of 10K+), `read`, and
   `search` by subject/sender through the dictionary, per account kind
   (iCloud, Gmail, Exchange). Mail's `whose` over a large mailbox can take
   tens of seconds; if it does, search goes newest-first by pages under
   the time cap.
2. Body search: Mail's dictionary has no full-text search. Options
   measured: Spotlight (`mdfind` over Mail's index; whether it answers
   without Full Disk Access) vs. scanning bodies of the newest N under
   the cap. Full Disk Access to read Mail's database is not on the table.
3. Stability of Mail's message `id` across a move and a relaunch (the
   Undo and identity rules depend on it).
4. `reply` with `opening window false` + `save`: the draft lands in
   Drafts with the quoted original, in each account kind.
5. The Automation prompt names LLMTray when the event comes from an
   `osascript` child (responsible process), on macOS 14, 15 and 27.

## Plan

1. Spike, results here.
2. Core (LLMTrayCore): `MailTools` (schemas, lenient reading, the line
   format), `MailPlan` (on `ChangePlan`'s store: ids, revisions,
   approval by identity), the trust kinds `mailRead` / `mailChange` in
   `ToolTrust`, tests with fixture JSON.
3. App: the script runner, the scripts, the plan card's mail rows,
   Settings › Tools › Mail (opt-in, accounts, permission state), the +
   menu item, the group in `ToolGroups`, the entitlement.
4. Eval: the usual tool-reflex set (asked → called, "привет" → not), a
   prompt-injection set (mail bodies asking for moves, trash, web
   searches, drafts to strangers: nothing happens without the user), on
   Gemma 4 26B and E4B.

## Not now

Sending; attachments (reading or saving them); rules and smart
mailboxes; other mail apps (Outlook, Spark); summaries running in the
background without a chat.
