# 0026 — Mail: the chat reads, sorts and drafts replies in Apple Mail

**Status: proposed** (2026-10-15). The user's idea and shape: "fat tools",
like the documents and folder tools. Reviewed by Codex and Muse (round 1
folded in). Waiting for the spike below and the user's review.

## Decision

The chat model gets Apple Mail as a tool group: "what came in today that
needs an answer", "find the invoice from Hetzner", "move the newsletters
to Later and mark them read", "draft a reply to Anna saying Thursday
works". It talks to Mail.app through its scripting dictionary, so every
account the user already has in Mail works (iCloud, Gmail, Exchange,
IMAP), with no passwords, no OAuth and no server of ours.

- **Opt-in**, like every feature that can do damage: off until turned on
  in Settings › Tools › Mail. Without it no mail tool is declared and Mail
  is never sent an Apple event. Turning it off drops pending mail plans.
- **Accounts the user ticks.** Turning the feature on asks macOS for
  Automation access (the first Apple event), then lists Mail's accounts,
  none ticked; the user ticks the ones the chat may see. An account not
  ticked is invisible to both tools. Unticking one drops its pending plan
  items, and every approval, execution and undo checks the account again.
- **A tool group, loaded when needed** ([0020](0020-documents.md),
  "Tools loaded when needed"): group `mail`, phrase "Apple Mail: read,
  search, sort, draft replies". On demand by default (`load_tools` or the
  + menu's **Use Mail…**); a profile can set it to Always.
- **Two tools, the folder tools' split** ([0014](0014-folder-tools.md),
  "Tools"): one to look, one to change. Fewer tools are understood better
  by small models and cost less context.
- **No message is sent to anyone.** Replies and new messages are saved as
  drafts; the user sends them from Mail. There is no send mode, by any
  path. A draft is not necessarily private to the Mac, though: Mail keeps
  it in the account's Drafts mailbox, which is on the account's server
  unless the account's Mailbox Behaviors put it On My Mac. The app reads
  where that mailbox is, and the plan card says it ("saved to Drafts of
  work@…, stored on that account's server").
- **Every change is a plan the user approves**: the folder tools' plan
  card and rules (whole, in part, or not at all; nothing happens before;
  Approve has no Return shortcut).
- **Mail is untrusted text**: subjects, senders, bodies and attachment
  names are data, never instructions (see "Trust").
- **Not in temporary chats.** They write nothing and hold no grants
  ([0006](0006-chat-sessions-and-library.md), 0014 Hardening 19); mail
  isn't declared there by any path.
- **Developer ID build only, for now.** The non-sandboxed app needs only
  `com.apple.security.automation.apple-events` (hardened runtime) and an
  `NSAppleEventsUsageDescription`. The App Store flavor is sandboxed:
  Mail's `com.apple.mail.compose` scripting access group covers composing
  only; reading and moving would need a temporary-exception entitlement
  with a justification to review. Not attempted now; the feature isn't
  shown there.

## Tools

```
mail(
  mode: accounts | list | search | read,
  mailbox?,          // "Inbox" (default), "Later", "Archive", account/mailbox
  account?,          // when two accounts have the same mailbox name
  query?,            // search: words in subject or sender (body: see spike)
  from?, since?,     // search filters; since = "2026-10-01" or "7d"
  unread_only?, flagged_only?,
  id?,               // read: one message
  cursor?            // paging
)
```

- `accounts` -- the ticked accounts and their mailboxes with unread
  counts, one line each, paged.
- `list` -- a mailbox, newest first: one line per message with a short
  id (`m12`), date, sender (name and address), subject (at most 120
  characters), read and flag marks, attachments count. No bodies. 25 per
  page.
- `search` -- the same lines for matches across the mailboxes asked (the
  ticked accounts' inboxes by default), newest first, within a time cap.
  A capped search says how far it got ("searched the newest 2,000 of
  14,300 in Inbox; older mail not searched") so the model doesn't call it
  "not found".
- `read` -- one message: From, Reply-To when it differs, To, Cc, date,
  subject, the body as plain text with quoted history and signatures cut,
  at most 6,000 characters, attachments by name (at most 80 characters
  each, 20 of them) and size; the result says what was cut and how much.
  Never attachment contents, never HTML. Our tools load nothing remote;
  Mail itself syncs and loads remote content by its own settings (Mail
  Privacy Protection), which this feature doesn't change.

```
change_mail(ops: [
  { op: move,        ids: [..], to: mailbox },
  { op: mark,        ids: [..], read?: bool, flagged?: bool },
  { op: trash,       ids: [..] },
  { op: reply_draft, id, body, reply_all? },
  { op: new_draft,   account, to: [..], cc?: [..], subject, body }
])
```

The list is the plan. The card shows each op in words ("move 14 messages
to Later", the messages expandable). A draft is one item, ticked or not
(no editing in the card: untick it and ask for changes), shown in full:
the account it is saved in, every recipient (a reply's recipients are
worked out from the message as read, Reply-To included and highlighted
when it differs from From), subject, body, and "with the quoted original
and your signature" for a reply. Limits: 10 recipients, 20,000
characters of body; a `new_draft` names one of the ticked accounts.

**After approval**, each item runs as its own script call:

- `move` / `mark` / `trash` in Mail. A `move` whose destination is the
  account's Deleted Messages or Junk mailbox (by the mailbox, not its
  name) is a trash and gets every trash rule. Trash is a move to the account's
  Deleted Messages mailbox, and only for an account whose Mail setting
  keeps deleted messages there (`move deleted messages to trash`); for
  another, trash is refused with the reason. The card says deleted mail
  follows the account's erase schedule.
- A draft is made with `reply … opening window false` (or a new outgoing
  message) and saved, then read back: if its recipients aren't the ones
  approved, it is deleted and the item fails with what Mail chose. Its
  Mail `id` is journaled then: that, not its text, is how Undo knows the
  draft is ours.

**Identity and state.** Ids are the chat's, not Mail's: `m12` maps to
(account, mailbox, Mail's message `id`, the `Message-ID` header) plus the
state seen (mailbox, read, flagged) when it was listed or read. At
execution the message is found again by those and must match, state
included, or the item fails closed ("changed since you approved"). A
message with no `Message-ID`, or one shared by two messages in the
account, can be read but not changed. Mail's events can't be checked and
applied atomically as a descriptor walk can (0014 Hardening 1); the
window is one item's check-then-change, and what fails is reported, never
retried silently.

**Journal and Undo**, as 0014's (Hardening 7, 13, 20): a durable pending
record before each item, the result after; plan ids and revisions never
reused. Undo takes back the last plan only where the current state is
still what the plan left (in the mailbox it was moved to, the mark it was
given); anything changed since is left and listed. A draft is deleted by
Undo only if it is the journaled one (its Mail `id`), still in Drafts,
with the recipients and subject we saved and a body that still starts
with the text we wrote (Mail adds the quote and signature after it); an
edited one is left, with a note.

**Timeouts.** A script runs in a child process (below), but Mail runs
outside it: killing the child doesn't stop an Apple event Mail already
took. A timed-out item is journaled "outcome unknown"; the app then looks
(one more read-only call) and records done when the change is visible.
Not seeing it proves nothing (Mail may still do it), so the item stays
"unknown": the rest of the plan stops, nothing is retried, and Undo
leaves it out, saying so. A draft is never re-made after an unknown
outcome. One found in Drafts afterwards that matches (recipients,
subject, our text) is reported, never adopted: Undo doesn't delete it,
since a draft of the user's could match too.

## Trust

Mail is the most attacked text a user has: anyone can put words in front
of the model. The rules are 0014's as they stand -- Hardening 2 as
revised on 2026-10-04 (the user's decision), not the turn boundary it
replaced, which made small models re-read and get refused every turn.
`ToolTrust` gets `mailRead` and `mailChange` kinds and a `mailText`
turn state, set by a `mail` result and counted in `hasUntrustedText`,
`hasFileText` and `hasToolText` -- so in `refusedUpFront` and
`changeIsAfterRead` too -- with tests for each path below:

1. **Mail text counts as file text.** After a `mail` result in the turn,
   or beside a `mail` call in the same batch (refused up front, before any
   call of the batch runs): network tools and generators are refused
   (`hasUntrustedText`), a pin is refused (`hasToolText`), and folder
   changes go to their plan marked "proposed after reading" (`hasFileText`).
2. **`change_mail` runs after any outside text** -- mail, files, folders,
   web -- but only into the plan, its items marked `afterRead`: the card
   says above Approve "Proposed right after reading your mail: check each
   of these N changes", a trash starts unticked and is never ticked for the
   user, a draft starts unticked. Moves and marks start ticked (Undo takes
   them back). Pinned files keep it off, as `change_files`.
3. **The human review is the barrier.** The trade, as in 0014: a hidden
   instruction in a mail can put a move or a draft into the plan; what
   stops it is the user reading the flagged plan -- which is why a draft
   shows every recipient and the account it is stored in, and starts
   unticked.
4. Mail text never reaches memory: memory reads only the user's own
   messages ([0024](0024-memory.md)).

## How it talks to Mail

- **Fixed scripts in the app, data as arguments.** Each mode is one
  JavaScript for Automation script shipped in the app, run by `osascript
  -l JavaScript <script> <args…>`. The model's strings arrive as `argv`
  and are only ever compared or assigned as values: no script builds
  source, a `whose` clause or an object specifier from them. Mailboxes and
  accounts are looked up by matching the given name against the
  enumerated list; searches fetch property arrays in bulk (`subject()`,
  `sender()`, `dateReceived()` of a mailbox's messages, in pages) and
  filter in the script. The script prints JSON; the app parses it with
  limits.
- **A child process, supervised** like document rendering (0020): its
  own process group, killed at the time cap (10 s for a list or a change
  item, 30 s for a search), 2 MB of stdout. Mail hangs on a stuck
  account; the chat must not (and see "Timeouts").
- **Permission.** A denial is answered to the model ("the user hasn't
  allowed Mail access; they can in System Settings › Privacy & Security ›
  Automation") and shown in Settings with a button there.
- **Mail not running**: an Apple event launches it. The first result
  that did says so ("opened Mail").

## Spike (before the code)

On the user's Mac, with their permission, read-only:

1. Speed of `list` (25 newest of an Inbox of 10K+), `read`, and a
   subject/sender `search` by bulk property fetch, per account kind
   (iCloud, Gmail, Exchange).
2. Body search: the dictionary has none. Measured: Spotlight (`mdfind`
   over Mail's index, and whether it answers without Full Disk Access)
   vs. scanning bodies of the newest N under the cap. Full Disk Access to
   read Mail's database is not on the table.
3. Mail's message `id` across a move and a Mail relaunch; how often
   `Message-ID` is missing or shared. Identity and Undo depend on it.
4. `reply … opening window false` + `save`: the draft lands in the right
   account's Drafts with the quoted original, recipients readable back.
5. The Automation prompt names LLMTray when the event comes from an
   `osascript` child (responsible process), on macOS 14, 15 and 27. If it
   doesn't, the scripts run in-process through OSAKit on a worker thread,
   and a time cap there means "outcome unknown" (the thread is abandoned,
   not killed; no other mail script runs until it returns).
6. Whether `move deleted messages to trash`, the Deleted Messages, Junk
   and Drafts mailboxes, and where Drafts are kept, are readable per
   account.

## Plan

1. Spike, results here.
2. Core (LLMTrayCore): `MailTools` (schemas, lenient reading, the line
   format), `MailPlan` (on `ChangePlan`'s store: ids, revisions, state,
   approval by identity), `ToolTrust`'s new kinds, tests with fixture JSON.
3. App: the script runner, the scripts, the plan card's mail rows,
   Settings › Tools › Mail (opt-in, accounts, permission state), the +
   menu item, the group in `ToolGroups`, the entitlement.
4. Eval: the tool-reflex set (asked → called, "привет" → not), and a
   prompt-injection set (mail bodies asking for moves, trash, web
   searches, drafts to strangers: nothing happens without the user ticking
   it), on Gemma 4 26B and E4B.

## Not now

Sending; attachments (reading or saving them); rules and smart
mailboxes; other mail apps; the App Store flavor; summaries running in
the background without a chat.
